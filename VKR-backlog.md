# VKR Backlog (Open Items, Backend-Only, Detailed)

Детализированный backend-only бэклог для доведения решения до целевого состояния VKR.  
Каждая задача содержит: контекст, целевые изменения, техническую декомпозицию, тесты, риски, зависимости и критерии приемки.

## Статусы

- `todo` — запланировано к реализации
- `blocked` — выполнение временно невозможно из-за внешней зависимости

## Соглашения по задачам

- Приоритет: `P0` (критично), `P1` (важно), `P2` (желательно).
- Оценка дана в идеальных инженерных днях (`i.d.`) без учета ожиданий ревью/CI.
- Для каждой задачи обязательны артефакты: код, тесты, документация (где применимо), evidence в traceability.

## 1. Backend parity и technical hardening

### BK-101. Синхронизация lifecycle клиента `bot -> scrapper`

- **Статус:** `todo`
- **Приоритет:** `P0`
- **Оценка:** `2-3 i.d.`
- **Почему:** Lifecycle клиента должен быть сквозным; сейчас `POST/DELETE /api/v1/clients` не гарантирует консистентную синхронизацию `bot` и `scrapper`.
- **Бизнес-цель:** исключить ситуации, где клиент зарегистрирован в одном сервисе и отсутствует во втором.
- **As-is (фактический разрыв):**
  - регистрация/удаление в `bot` не полностью привязана к `registerChat/unregisterChat` в `scrapper`;
  - нет формализованной стратегии компенсации при partial failure.
- **To-be (целевое состояние):**
  - атомарная с точки зрения бизнес-инварианта операция lifecycle между сервисами;
  - документированная политика компенсации.
- **Затрагиваемые области:**
  - `bot/src/main/java/backend/academy/bot/controller/BotRestController.java`
  - `bot/src/main/java/backend/academy/bot/service/ClientOperationService.java`
  - `bot/src/main/java/backend/academy/bot/service/ScrapperConnectionService.java`
  - интеграционные тесты `bot`
- **Техническая декомпозиция:**
  1. Зафиксировать orchestration-поток для `POST/DELETE /api/v1/clients` (последовательность вызовов и точки отказа).
  2. Реализовать обязательные вызовы `registerChat(login,password)`/`unregisterChat(login,password)` в основном бизнес-потоке.
  3. Реализовать компенсацию:
     - если второй шаг падает, откатывать первый или помечать в recoverable-state с немедленным retry;
     - исключить "тихую" неконсистентность.
  4. Уточнить ошибки для клиента API (что именно возвращаем при частичном сбое).
  5. Добавить idempotency-проверки на повторные вызовы.
- **Тест-план:**
  - Integration:
    - happy-path register/unregister;
    - fail-after-first-step register;
    - fail-after-first-step unregister;
    - repeat-call idempotency;
  - Contract:
    - стабильные коды/тела ошибок при partial failure.
- **Риски:**
  - временные race-condition при параллельных вызовах для одного логина;
  - двойная компенсация при retry.
- **Смягчение рисков:**
  - serialization per client key (или optimistic control + уникальные ограничения);
  - явный correlation id в логах операции.
- **Артефакты приемки:**
  - PR с orchestration-логикой;
  - интеграционные тесты;
  - секция в README/архитектурных заметках про lifecycle.
- **Definition of Done:** lifecycle клиента сквозной, консистентный и тестируемо устойчивый к partial failure.
- **Зависимости:** нет

### BK-102. Строгая runtime-валидация DTO по OpenAPI

- **Статус:** `todo`
- **Приоритет:** `P0`
- **Оценка:** `2-3 i.d.`
- **Почему:** ограничения OpenAPI (`minLength`, `uri`, `uniqueItems`) должны выполняться в runtime одинаково во всех входных точках.
- **Бизнес-цель:** исключить прием некорректных данных и неявную "автокоррекцию" входа.
- **As-is:**
  - в части DTO отсутствуют необходимые Bean Validation ограничения;
  - не везде есть `@Valid` на `@RequestBody`;
  - для дублей `tags/filters` не всегда возвращается явный `400`.
- **To-be:**
  - валидация входа полностью соответствует контракту;
  - все нарушения валидации приводят к предсказуемому `400`.
- **Затрагиваемые области:**
  - `scrapper-bot-connectivity/.../model/request/*.java`
  - контроллеры `bot` и `scrapper` с входными DTO
  - обработка ошибок валидации
  - контрактные/интеграционные тесты
- **Техническая декомпозиция:**
  1. Провести DTO-to-OpenAPI gap review (таблица полей и ограничений).
  2. Добавить недостающие аннотации:
     - `@NotBlank`, `@NotNull`, ограничения длины;
     - валидация URI/URL;
     - запрет дублей коллекций (кастомный валидатор или явная проверка).
  3. Проставить `@Valid` в контроллерах на все соответствующие входы.
  4. Централизовать обработку ошибок валидации (единый формат ответа).
  5. Удалить "молчаливую нормализацию" дублей, заменить на `400`.
- **Тест-план:**
  - Negative contract tests:
    - пустые обязательные поля;
    - некорректный URI;
    - дубли tags/filters;
  - Regression:
    - валидные payload продолжают работать.
- **Риски:**
  - изменение поведения может сломать текущие клиентские сценарии с "грязными" данными.
- **Смягчение рисков:**
  - заранее зафиксировать список breaking validation changes в changelog.
- **Артефакты приемки:**
  - обновленные DTO/контроллеры;
  - набор негативных тестов;
  - краткая таблица соответствия OpenAPI ограничениям.
- **Definition of Done:** все ограничения OpenAPI enforce-ятся в runtime и покрыты негативными тестами.
- **Зависимости:** `BK-101` (желательно)

### BK-103. Унификация ошибок `/updates` в `ApiErrorResponse`

- **Статус:** `todo`
- **Приоритет:** `P0`
- **Оценка:** `1-2 i.d.`
- **Почему:** ошибки internal auth должны иметь тот же контракт ответа, что и остальные API-ошибки.
- **Бизнес-цель:** единый формат ошибок для предсказуемости клиентов и трассировки.
- **As-is:** для части auth-ошибок используется `ResponseStatusException` без обязательной унификации тела.
- **To-be:** `401/403` для `/updates` возвращаются через доменные исключения и `ApiErrorResponse`.
- **Затрагиваемые области:**
  - `bot/.../controller/ScrapperController.java`
  - `bot/.../controller/GlobalExceptionControllerHandler.java`
  - integration tests для `/updates`
- **Техническая декомпозиция:**
  1. Выделить доменные исключения для auth failure (`missing header`, `invalid secret`).
  2. Подключить обработку в global exception handler.
  3. Гарантировать одинаковые поля `ApiErrorResponse` для `401` и `403`.
  4. Добавить логирование причины отказа без утечки секрета.
- **Тест-план:**
  - `missing header` -> `401` + корректная структура тела;
  - `invalid secret` -> `403` + корректная структура тела;
  - no-secret-in-body/log assertion (где возможно).
- **Риски:** случайная утечка auth-деталей в сообщение ошибки.
- **Смягчение рисков:** sanitize error messages и запрет логирования сырого секрета.
- **Артефакты приемки:** integration tests + снимки формата ошибок.
- **Definition of Done:** `/updates` отдает `ApiErrorResponse` для всех auth-ошибок без исключений.
- **Зависимости:** нет

### BK-104. Conditional polling GitHub: `ETag` + `If-Modified-Since`

- **Статус:** `todo`
- **Приоритет:** `P0`
- **Оценка:** `2-4 i.d.`
- **Почему:** целевая VKR-модель требует полноценного conditional polling, а не только частичной ETag-реализации.
- **Бизнес-цель:** уменьшить лишние обращения и корректно интерпретировать отсутствие изменений.
- **As-is:** используется ETag, но `If-Modified-Since` и связанный poll-state доведены не полностью.
- **To-be:**
  - запросы к GitHub отправляются с корректной комбинацией `If-None-Match` и `If-Modified-Since`;
  - состояние (etag/last-modified/last-checked) корректно обновляется.
- **Затрагиваемые области:**
  - `scrapper/.../client/GithubClient.java`
  - `scrapper/.../service/updaters/impl/GithubUpdaterService.java`
  - слой хранения poll-state
  - unit/integration tests для GitHub updater
- **Техническая декомпозиция:**
  1. Расширить модель состояния GitHub polling (`etag`, `last-modified`, `last_checked_at`).
  2. Обновить клиент: добавить `If-Modified-Since` при наличии значения.
  3. Зафиксировать порядок приоритета заголовков и обновление состояния после `200/304`.
  4. Учесть деградационные случаи: stale headers, пустые ответы, временные 5xx.
  5. Добавить миграции/изменения репозитория состояния (если требуется).
- **Тест-план:**
  - Unit:
    - заголовки формируются корректно;
    - `304` не создает ложных апдейтов;
  - Integration:
    - `200` обновляет состояние;
    - `304` сохраняет консистентность poll-state.
- **Риски:**
  - рассинхрон между БД-состоянием и заголовками;
  - ложные negative updates из-за неверной обработки `304`.
- **Смягчение рисков:** строгие state-transition тесты и явные инварианты в коде.
- **Артефакты приемки:** код + тесты + документированная схема state transitions.
- **Definition of Done:** GitHub polling соответствует VKR-логике conditional headers и стабилен под тестами.
- **Зависимости:** нет

### BK-109. JSON-логирование для production-профиля

- **Статус:** `todo`
- **Приоритет:** `P1`
- **Оценка:** `1-2 i.d.`
- **Почему:** эксплуатация и защита требуют машинно-обрабатываемых структурированных логов.
- **Бизнес-цель:** ускорить диагностику, анализ инцидентов и интеграцию с log pipelines.
- **As-is:** нет явной production-конфигурации JSON-логирования.
- **To-be:**
  - отдельный prod-профиль с JSON encoder;
  - documented run instructions.
- **Затрагиваемые области:**
  - `bot` logging config
  - `scrapper` logging config
  - `README` и/или runbook
- **Техническая декомпозиция:**
  1. Выбрать и подключить JSON encoder (например, logstash-logback-encoder).
  2. Добавить конфиги логгера с полями: timestamp, level, service, trace/span/request identifiers.
  3. Развести dev/readable и prod/json режимы.
  4. Добавить безопасную маскировку секретов.
  5. Обновить документацию запуска и пример чтения логов.
- **Тест-план:**
  - Smoke: запуск с prod-профилем -> проверка JSON-формата строки;
  - Regression: dev-профиль остается человекочитаемым.
- **Риски:**
  - деградация производительности из-за лишних полей;
  - случайная утечка чувствительных данных.
- **Смягчение рисков:** минимальный обязательный набор полей + masking filters.
- **Артефакты приемки:** конфиги логирования, README/runbook обновления, пример output.
- **Definition of Done:** production-профиль генерирует валидный JSON-лог и документирован для эксплуатации.
- **Зависимости:** `BK-104` (желательно)

### BK-503. Финальный traceability-аудит `VKR -> code -> tests`

- **Статус:** `todo`
- **Приоритет:** `P0`
- **Оценка:** `1-2 i.d.`
- **Почему:** соответствие VKR должно быть не декларативным, а проверяемым через связь требований с кодом и тестами.
- **Бизнес-цель:** формальный evidence package для защиты/приемки.
- **As-is:** матрица есть, но должна быть доведена до финального состояния с учетом всех открытых задач.
- **To-be:** полная матрица трассировки для backend-требований и НФТ.
- **Затрагиваемые области:**
  - `docs/quality/traceability-matrix.md`
  - `docs/quality/backend-test-matrix.md`
  - `docs/quality/defense-acceptance-checklist.md`
- **Техническая декомпозиция:**
  1. Зафиксировать финальный перечень backend-требований VKR.
  2. Для каждого требования заполнить:
     - реализация (файл/модуль/компонент);

- **Смягчение рисков:** каждая строка матрицы должна иметь конкретный артефакт-подтверждение.
- **Артефакты приемки:** финальная traceability-матрица и checklist для защиты.
- **Definition of Done:** каждое backend-требование VKR имеет проверяемую связь `требование -> код -> тест`.
- **Зависимости:** `BK-109`

### BK-504. Финальная верификация решения

- **Статус:** `todo`
- **Приоритет:** `P0`
- **Оценка:** `1 i.d.`
- **Почему:** финальная приемка требует зафиксированных результатов прогонов, а не только наличия кода.
- **Бизнес-цель:** подтвердить, что система стабильно работает в целевом backend-контуре.
- **As-is:** процедуры верификации описаны, но нужен финальный консолидированный прогон.
- **To-be:** завершенный verification pass с evidence.
- **Затрагиваемые области:**
  - CI workflows
  - локальные/стендовые smoke-процедуры
  - quality docs с результатами
- **Техническая декомпозиция:**
  1. Выполнить `./mvnw clean verify` (или эквивалентный pipeline) и сохранить результаты.
  2. Выполнить smoke backend в `docker compose`:
     - health endpoints;
     - ключевые API сценарии;
     - проверка очередей/доставки в выбранном режиме.
  3. Выполнить smoke на staging:
     - deploy;
     - health-check;
     - rollback readiness.
  4. Зафиксировать результаты в acceptance checklist.
- **Тест-план (приемочный):**
  - all-green unit/integration/contract suite;
  - smoke сценарии без критичных дефектов.
- **Риски:**
  - flaky тесты дают ложное впечатление нестабильности;
  - окружение staging не соответствует production-like конфигурации.
- **Смягчение рисков:** повторяемый прогон + фиксация окружения и версии артефактов.
- **Артефакты приемки:**
  - logs/summary из verify;
  - smoke-протокол;
  - обновленный defense checklist.
- **Definition of Done:** есть формализованный финальный пакет evidence, подтверждающий техническую готовность backend к защите.
- **Зависимости:** `BK-503`

## Definition of Done (Target Solution, Backend-Only)

- Закрыты критические backend-gap’ы по lifecycle, валидации, auth-ошибкам и conditional polling.
- Логирование в production работает в структурированном JSON-формате.
- Runtime поддерживает управляемый режим доставки `http|kafka` без двусмысленного поведения.
- В репозитории актуальны инфраструктурные артефакты (`k8s`, CI/CD, runbooks, `.env.example`) и они согласованы с документацией.
- Сформирована финальная traceability-матрица `VKR -> code -> tests` по backend-требованиям.
- Выполнена финальная верификация (`verify + smoke`) с зафиксированными evidence для защиты.
