# VKR Backlog (Prioritized)

Операционный backlog для приведения проекта к целевому решению из `VKR.pdf`.
Документ сфокусирован на практическом исполнении: приоритет, результат, зона изменений и зависимости.

## Правила приоритизации

- `P0` - критичный путь: без выполнения нельзя получить рабочее целевое решение.
- `P1` - высокий приоритет: функциональная и архитектурная полнота, качество и безопасность.
- `P2` - стабилизация и выпуск: инфраструктура, тестовая зрелость, финальная приемка.

## P0 (Critical Path)

Смысл блока: минимально необходимый набор для рабочего целевого контура `scrapper -> bot` с сохранением данных и Kafka-веткой.

### P0-1. Bot persistence (клиенты + уведомления)

- **Цель:** сделать `bot` самостоятельным сервисом хранения клиентов и уведомлений.
- **Подзадачи:**
  - добавить в `bot` зависимости для БД и миграций;
  - завести datasource-конфиг и профили локального/тестового запуска;
  - создать миграции таблиц `clients` и `notifications` (и индексы под частые запросы);
  - реализовать слой repository/service для клиентов и уведомлений;
  - переключить `BotRestController` и `ScrapperController` на новую persistence-логику;
  - добавить маппинг DTO `LinkUpdate -> NotificationEntity`.
- **Definition of Done:**
  - в `bot` подключены DB-зависимости и миграции;
  - создана схема хранения клиентов и уведомлений;
  - `POST/DELETE /api/v1/clients` работают через БД `bot`;
  - входящие `LinkUpdate` сохраняются как уведомления.
- **Проверки:**
  - интеграционный тест регистрации/удаления клиента с реальной БД;
  - интеграционный тест сохранения уведомления через `POST /updates`;
  - проверка каскадного удаления данных клиента.
- **Артефакты результата:**
  - миграции `bot`;
  - новые/обновленные сервисы и репозитории;
  - тесты по клиентам и уведомлениям.
- **Зона кода:**
  - `bot/pom.xml`
  - `bot/src/main/resources/application.yaml`
  - `bot/src/main/resources/db/**`
  - `bot/src/main/java/backend/academy/bot/**` (service/repository/controller)
- **Зависимости:** нет (стартовая задача критичного пути).
- **Риск:** расхождение между проксируемой логикой и локальным состоянием данных `bot`.

### P0-2. Kafka intake в Bot + единый pipeline обработки уведомлений

- **Цель:** обеспечить прием `LinkUpdate` не только по HTTP, но и по Kafka.
- **Подзадачи:**
  - подключить `spring-kafka` и consumer-конфиги (`group-id`, topic, deserializer, retry);
  - реализовать Kafka listener для `LinkUpdate`;
  - выделить единый use-case/сервис обработки уведомлений;
  - переподключить HTTP `/updates` на тот же use-case;
  - обеспечить идемпотентность записи уведомлений (или dedup-политику).
- **Definition of Done:**
  - в `bot` подключен Kafka consumer;
  - сообщения `LinkUpdate` из Kafka обрабатываются тем же сервисом, что и HTTP `/updates`;
  - поведение хранения уведомлений одинаковое для HTTP и Kafka.
- **Проверки:**
  - integration test: публикация события в Kafka -> запись в БД `bot`;
  - regression test: HTTP `/updates` дает тот же результат, что и Kafka;
  - test на некорректный payload/десериализацию.
- **Артефакты результата:**
  - listener и Kafka config;
  - общий сервис обработки уведомлений;
  - e2e тесты двух каналов входа.
- **Зона кода:**
  - `bot/pom.xml`
  - `bot/src/main/resources/application.yaml`
  - `bot/src/main/java/backend/academy/bot/config/**`
  - `bot/src/main/java/backend/academy/bot/**` (listener/service/controller)
- **Зависимости:** `P0-1`.
- **Риск:** двойная доставка из разных каналов без единой дедупликации.

### P0-3. Outbox runtime в Scrapper (publisher + mark sent)

- **Цель:** довести Transactional Outbox до рабочего режима доставки.
- **Подзадачи:**
  - добавить outbox processor (scheduler/worker) для пачечной выборки `sent=false`;
  - реализовать отправку в Kafka с обработкой ошибок и retry-policy;
  - обновлять `sent`, `sent_at`, `attempt_count` по результату публикации;
  - унифицировать имя topic через конфиг (убрать hardcoded значения);
  - добавить метрики/логи по backlog outbox.
- **Definition of Done:**
  - фоновый процесс читает `kafka_outbox` по `sent = false`;
  - сообщения публикуются в Kafka;
  - после успеха обновляются `sent`, `sent_at`, `attempt_count`;
  - topic берется из конфигурации, без hardcode.
- **Проверки:**
  - integration test: запись в outbox -> публикация -> `sent=true`;
  - test на ошибку брокера: рост `attempt_count`, повторная попытка;
  - test на восстановление после рестарта сервиса.
- **Артефакты результата:**
  - outbox processor;
  - SQL/репозиторные методы для выборки и update-статуса;
  - интеграционные тесты надежной доставки.
- **Зона кода:**
  - `scrapper/src/main/java/backend/academy/scrapper/service/**`
  - `scrapper/src/main/java/backend/academy/scrapper/db/repository/**`
  - `scrapper/src/main/resources/application.yaml`
  - `scrapper/src/main/resources/db/query/kafka_outbox/**`
- **Зависимости:** желательно после `P0-2`, чтобы была готова целевая Kafka-цепочка.
- **Риск:** потеря/дублирование сообщений при неверной транзакционной границе.

## P1 (High Priority)

Смысл блока: закрытие функциональных и нефункциональных требований ВКР поверх уже рабочего P0-контура.

### P1-1. Безопасность: BCrypt и единый auth flow

- **Цель:** закрыть требования по хранению паролей и аутентификации.
- **Подзадачи:**
  - добавить `PasswordEncoder` и унифицированный сервис проверки credentials;
  - мигрировать хранение паролей на hash (с обратимой/плавной стратегией перехода);
  - убрать прямые SQL-проверки `login+password` в open text;
  - синхронизировать поведение `bot` и `scrapper` по auth-ошибкам и кодам ответов;
  - уточнить политику межсервисной аутентификации (минимум shared secret/header).
- **Definition of Done:**
  - plain-text пароли исключены в `bot` и `scrapper`;
  - пароли хранятся в hash-виде (BCrypt);
  - проверка аутентификации согласована для клиентских операций.
- **Проверки:**
  - unit tests для encode/matches;
  - integration tests на успешную и неуспешную аутентификацию;
  - проверка миграции существующих пользователей.
- **Артефакты результата:**
  - миграции безопасности;
  - auth-сервис и обновленные репозитории;
  - тесты auth-сценариев.
- **Зона кода:**
  - `bot/src/main/java/backend/academy/bot/**`
  - `scrapper/src/main/java/backend/academy/scrapper/**`
  - миграции обоих сервисов (`*/src/main/resources/db/**`)
- **Зависимости:** `P0-1` (наличие БД в `bot`).
- **Риск:** несовместимость с уже созданными учетными записями.

### P1-2. Polling-state и runtime-логика опроса

- **Цель:** синхронизировать фактический polling-процесс с целевой моделью состояния.
- **Подзадачи:**
  - обновлять `last_checked_at` для каждой обработанной ссылки;
  - внедрить чтение/обновление `poll_state` (retry_count/backoff/last_success);
  - исключать ссылки из активной выборки, если действует backoff;
  - формализовать правила update состояния для GitHub и StackOverflow.
- **Definition of Done:**
  - `last_checked_at` корректно обновляется в каждом цикле;
  - `poll_state` используется в runtime (retry/backoff/last-success);
  - scheduler выбирает ссылки с учетом состояния опроса.
- **Проверки:**
  - integration tests на выборку ссылок с backoff;
  - test на корректный update state при успехе/ошибке;
  - regression test на отсутствие повторной обработки одного и того же окна.
- **Артефакты результата:**
  - обновленный scheduler и сервисы опроса;
  - query-изменения по выборке;
  - покрытие poll-state тестами.
- **Зона кода:**
  - `scrapper/src/main/java/backend/academy/scrapper/service/listeners/LinkUpdateScheduledListener.java`
  - `scrapper/src/main/java/backend/academy/scrapper/service/impl/**`
  - `scrapper/src/main/java/backend/academy/scrapper/db/**`
  - `scrapper/src/main/resources/db/query/links/**`
- **Зависимости:** `P0-3`.
- **Риск:** неправильная логика backoff может заморозить часть ссылок.

### P1-3. Фильтрация получателей по client filters

- **Цель:** формировать `clientsIds` только из релевантных подписчиков.
- **Подзадачи:**
  - определить и зафиксировать поддерживаемый набор фильтров (`author`, `label`, `type`);
  - реализовать parser/validator фильтров формата `key:value`;
  - встроить фильтрацию в pipeline построения `LinkUpdate`;
  - добавить fallback-поведение для неизвестных фильтров (лог + skip rule/strict fail).
- **Definition of Done:**
  - при обнаружении события применяются фильтры подписки (`author`, `label` и т.п.);
  - нерелевантные клиенты не попадают в `clientsIds`;
  - поведение покрыто тестами на разные типы событий.
- **Проверки:**
  - unit tests filter-engine;
  - integration tests на GitHub/StackOverflow events;
  - test на конфликтующие фильтры и пустые фильтры.
- **Артефакты результата:**
  - фильтр-движок/расширение текущей логики;
  - тест-наборы по типам фильтров;
  - обновленная документация по формату фильтров.
- **Зона кода:**
  - `scrapper/src/main/java/backend/academy/scrapper/service/updaters/**`
  - `scrapper/src/main/java/backend/academy/scrapper/service/impl/**`
  - `scrapper/src/main/java/backend/academy/scrapper/db/repository/**`
- **Зависимости:** `P1-2`.
- **Риск:** рост сложности и ложные срабатывания фильтров.

### P1-4. Контрактная консистентность OpenAPI/AsyncAPI и runtime

- **Цель:** устранить расхождения между контрактами и фактическим поведением API/топиков.
- **Подзадачи:**
  - составить diff contract vs runtime для `bot` и `scrapper`;
  - выровнять DTO и коды ответов (особенно 400/404);
  - синхронизировать имена топиков и payload для Kafka-канала;
  - добавить contract tests для критичных endpoint-ов и сообщений.
- **Definition of Done:**
  - OpenAPI и контроллеры возвращают согласованные коды и DTO;
  - AsyncAPI соответствует фактическим топикам и payload;
  - обработка ошибок 400/404 единообразна в `bot` и `scrapper`.
- **Проверки:**
  - tests на response codes и schema;
  - smoke-проверка генерации/валидации контрактов;
  - интеграционная проверка публикации/чтения Kafka по AsyncAPI.
- **Артефакты результата:**
  - обновленные contract-файлы;
  - исправленные controllers/handlers;
  - contract test suite.
- **Зона кода:**
  - `bot/contracts/openapi.yaml`
  - `scrapper/contracts/openapi.yaml`
  - `scrapper/contracts/asyncapi.yaml`
  - контроллеры/handler-ы в `bot` и `scrapper`.
- **Зависимости:** `P0-2`, `P0-3`.
- **Риск:** ломка обратной совместимости для текущих клиентов.

## P2 (Stabilization & Release)

Смысл блока: доведение решения до состояния стабильного релиза и защиты.

### P2-1. Инфраструктура локального окружения под целевую топологию

- **Цель:** привести локальный запуск к архитектуре ВКР.
- **Подзадачи:**
  - разделить БД в `docker-compose` на `bot-db` и `scrapper-db`;
  - добавить Kafka/Zookeeper или совместимый стек брокера;
  - привести env-переменные к единой схеме именования;
  - актуализировать healthcheck и зависимости запуска;
  - валидировать сценарий `docker compose up` с нуля.
- **Definition of Done:**
  - `docker-compose` поднимает `bot`, `scrapper`, две БД и Kafka-окружение;
  - env-переменные согласованы между сервисами;
  - убраны заведомо опасные fallback-конфиги.
- **Проверки:**
  - чистый локальный подъем без ручных шагов;
  - успешный smoke для ключевых API;
  - проверка доступности Kafka-канала.
- **Артефакты результата:**
  - обновленный `docker-compose.yaml`;
  - синхронизированные `application.yaml`;
  - обновленная инструкция запуска.
- **Зона кода:**
  - `docker-compose.yaml`
  - `bot/src/main/resources/application.yaml`
  - `scrapper/src/main/resources/application.yaml`
  - `scrapper/src/main/java/backend/academy/scrapper/config/ClientConfig.java`
- **Зависимости:** `P0-2`, `P0-3`.
- **Риск:** нестабильный локальный стенд из-за гонок старта контейнеров.

### P2-2. Integration/E2E тесты по критичному контуру

- **Цель:** зафиксировать поведение и защититься от регрессий.
- **Подзадачи:**
  - включить/переписать отключенные `@Disabled` тесты в `bot`;
  - добавить e2e сценарии на полный путь от подписки до получения уведомления;
  - покрыть отдельно HTTP-mode и Kafka-mode;
  - добавить сценарии retry/outbox/failure-path;
  - встроить запуск в CI с отдельным stage.
- **Definition of Done:**
  - отключенные тесты в `bot` переактивированы или заменены эквивалентом;
  - есть сценарии HTTP/Kafka доставки, outbox retry, 400/404, subscribe/unsubscribe;
  - CI подтверждает прохождение интеграционных сценариев.
- **Проверки:**
  - стабильный прогон на чистом окружении минимум 3 раза подряд;
  - отчет тестов с разделением unit/integration/e2e;
  - фиксация времени выполнения и флак-факторов.
- **Артефакты результата:**
  - интеграционные и e2e тесты;
  - CI-конфиг с отдельным тестовым джобом;
  - тестовая матрица сценариев.
- **Зона кода:**
  - `bot/src/test/**`
  - `scrapper/src/test/**`
  - test config/resources в обоих модулях
- **Зависимости:** `P0-*`, `P1-*`.
- **Риск:** флаки тесты из-за внешних зависимостей и таймингов.

### P2-3. Финальная приемка по DoD ВКР

- **Цель:** зафиксировать завершенность проекта перед защитой.
- **Подзадачи:**
  - провести итоговый аудит по пунктам F1-F15;
  - собрать демонстрационный сценарий (happy path + failure path);
  - зафиксировать traceability: требование -> реализация -> тест;
  - подготовить финальный release checklist.
- **Definition of Done:**
  - выполнены все пункты общего DoD из `VKR-plan.md`;
  - подготовлен финальный чек-лист демонстрации сценариев;
  - подтверждена соответствие функциональным и ключевым нефункциональным требованиям.
- **Проверки:**
  - формальный чек-лист приемки закрыт на 100%;
  - подтверждающие ссылки на код/контракты/тесты собраны в одном документе;
  - итоговый локальный и CI прогон успешен.
- **Артефакты результата:**
  - финальный acceptance checklist;
  - обновленный `README.md` и сопроводительные документы;
  - пакет доказательств соответствия ВКР.
- **Зона кода и артефактов:**
  - `VKR-plan.md`
  - `README.md`
  - контракты, тесты, compose-конфигурация
- **Зависимости:** `P2-1`, `P2-2`.
- **Риск:** неполная трассировка «требование -> тест» перед защитой.

## Риски

- Высокая связность изменений между `bot` и `scrapper` при миграции на Kafka-путь.
- Риск контрактных регрессий при выравнивании OpenAPI/AsyncAPI и runtime.
- Рост сложности тестового окружения после добавления второй БД и Kafka в compose.
- Потенциальные проблемы миграции данных при переходе на hash-пароли.
